# 最佳实践

> 如果你刚开始接触 Codex 或编程智能体，本指南将帮助你更快地获得更好的结果。

Codex 在以下情况下表现最佳：你不要把它当作一次性的助手，而是当作一个你可以持续配置和优化的**队友**。

## 从上下文和提示开始

即使提示不完美，Codex 也已经足够强大。但清晰的提示能让结果更可靠。一个好的提示应包含四部分：

| 要素 | 说明 |
| --- | --- |
| **目标** | 你想要改变或构建什么？ |
| **上下文** | 哪些文件、文件夹、文档、示例或错误与此任务相关？可以用 `@` 引用特定文件 |
| **约束** | 应遵循哪些标准、架构、安全要求或约定？ |
| **完成条件** | 任务完成前应满足什么条件？（如测试通过、行为改变、bug 不再复现） |

### 选择推理级别

| 级别 | 适用场景 |
| --- | --- |
| **低** | 快速、边界清晰的任务 |
| **中/高** | 更复杂的变更或调试 |
| **极高** | 长时间、智能体驱动、推理密集型任务 |

:::tip
在 Codex 桌面应用中尝试使用语音听写，而不是打字输入。
:::

## 困难任务先规划

如果任务复杂、模糊或难以描述清楚，让 Codex 先规划再编码。

**Plan 模式：** 对大多数用户来说，这是最简单有效的选择。Plan 模式让 Codex 收集上下文、提出澄清性问题，并在实施前构建更强的计划。使用 `/plan` 或 `Shift+Tab` 切换。

**让 Codex 先提问：** 如果你只有一个粗略的想法，让 Codex 先问你问题。让它挑战你的假设，把模糊的想法变成具体的东西。

**使用 PLANS.md 模板：** 对于更高级的工作流，配置 Codex 遵循 PLANS.md 或执行计划模板。

## 用 AGENTS.md 复用指南

一旦某个提示模式有效，下一步就是停止手动重复。这就是 AGENTS.md 的作用——它是面向智能体的开放式 README，自动加载到上下文中。

一个好的 AGENTS.md 应包含：
- 仓库布局和重要目录
- 如何运行项目
- 构建、测试和 lint 命令
- 工程规范和 PR 期望
- 约束条件和禁止规则
- 完成定义和验证方法

使用 CLI 中的 `/init` 命令可在当前目录快速搭建 AGENTS.md 模板。

<Tabs>
  <TabItem label="全局">
    `~/.codex/AGENTS.md` — 个人默认设置
  </TabItem>
  <TabItem label="仓库级">
    `<repo>/.codex/AGENTS.md` — 团队共享标准

  </TabItem>
</Tabs>

:::tip
当 Codex 两次犯同样的错误时，让它做个回顾并更新 AGENTS.md。
:::

## 配置 Codex 保持一致性

配置是让 Codex 在会话间保持行为一致的主要方式。

| 配置层 | 位置 |
| --- | --- |
| 个人默认 | `~/.codex/config.toml` |
| 仓库特定 | `.codex/config.toml` |
| 命令行覆盖 | 临时一次性使用 |

**审批模式** 控制 Codex 何时征求你的许可才能运行命令。
**沙箱模式** 控制 Codex 能否读取或写入目录中的文件。

:::note
CLI、IDE 和 Codex 桌面应用共享相同的配置层。
:::

## 通过测试和审查提高可靠性

不要止步于让 Codex 做出变更。让它：
- 编写或更新测试
- 运行相关的测试套件
- 检查 lint、格式或类型检查
- 确认最终行为符合要求
- 审查差异中的 bug、回归或风险模式

使用 `/review` 命令进行代码审查。

## 用 MCP 连接外部上下文

当 Codex 需要的上下文在仓库外部时，使用 MCP（模型上下文协议）。MCP 将 Codex 连接到你已经使用的工具和系统。

**适合使用 MCP 的场景：**
- 所需上下文在仓库外部
- 数据频繁变化
- 希望 Codex 使用工具而非粘贴的指令
- 需要跨用户或项目可重复的集成

## 将重复工作转化为技能

一旦工作流变得可重复，将其打包为技能（Skill）。技能在 CLI、IDE 扩展和 Codex 桌面应用中均可使用。

一个好的经验法则：如果你反复使用相同的提示或纠正相同的工作流，它应该成为一个技能。

**适合技能的场景：**
- 日志分类
- 发布说明撰写
- 对照清单的 PR 审查
- 迁移规划
- 遥测或事故总结

## 用自动化处理稳定工作流

一旦工作流稳定下来，你可以安排 Codex 在后台自动运行。

**适合自动化的场景：**
- 汇总最近的提交
- 扫描潜在 bug
- 起草发布说明
- 检查 CI 失败
- 生成站会摘要
- 按计划运行可重复的分析工作流

:::tip
技能定义方法，自动化定义时间表。先让工作流可靠，再自动化。
:::

## 用会话控制组织长时工作

每个任务保持一个线程。如果工作仍属于同一问题，留在同一线程中通常更好。只有当工作真正分叉时才 fork。

使用子智能体工作流将边界清晰的工作从主线程卸载。让主智能体专注于核心问题。

**有用的斜杠命令：**

| 命令 | 作用 |
| --- | --- |
| `/resume` | 恢复保存的对话 |
| `/fork` | 创建新线程并保留原始记录 |
| `/compact` | 压缩过长的对话上下文 |
| `/agent` | 在并行智能体间切换活动线程 |
| `/status` | 检查当前会话状态 |

## 常见错误

- ❌ 在提示中塞入持久化规则，而不是移到 AGENTS.md 或技能中
- ❌ 不给智能体提供构建和测试命令的细节，导致它无法验证自己的工作
- ❌ 在多步骤和复杂任务上跳过规划
- ❌ 在理解工作流之前就给 Codex 计算机的完全权限
- ❌ 在不使用 Git 工作树的情况下对同一文件运行活动线程
- ❌ 在手动验证可靠性之前就把周期性任务转为自动化
- ❌ 把 Codex 当作需要一步步盯着看的东西，而不是与你自己的工作并行使用
- ❌ 每个项目用一个线程，而不是每个任务用一个线程（导致上下文膨胀）
